Menu CRUD — UI patterns

Five approaches for add / edit / delete, with tradeoffs.

1. Table + modal 2. Inline table 3. Master-detail 4. Cards + drawer 5. Dedicated page

Each section below is a working mockup of one approach to managing menu items. Click around — open modals, edit inline, select a row, etc. Tradeoffs are listed under each design. The data is shared in memory across designs so you can see edits reflected as you switch between them.

Design 1

Table with modal dialog

A scannable table. Add/Edit open a modal form; Delete prompts a confirm dialog.

Item Tags Price Actions

Pros

  • Familiar admin pattern — low learning curve.
  • Scales well to hundreds of rows with sort/filter.
  • Modal isolates the form — clear save/cancel intent.

Cons

  • Context switch: modal hides the list while editing.
  • Modals are awkward on mobile and for long forms.
  • Not deep-linkable — refreshing loses your place.

Best for

  • Power users doing occasional edits.
  • Short, simple forms (≤8 fields).
  • Data-dense back-office tools.

Design 2

Inline editable table

Click any cell to edit it in place. Add row at the bottom. Delete via a row action.

Name Description Price

Pros

  • Fastest pattern for bulk edits — no modal trips.
  • Spreadsheet-like, great for tweaking many prices.
  • No context loss — you can see neighboring rows.

Cons

  • Discoverability — users may not realize cells are editable.
  • Validation/error UI is cramped inside a cell.
  • Hard to support rich fields (tag pickers, image upload).
  • Accidental edits are easy; needs robust undo.

Best for

  • Frequent tabular edits (price changes, reorders).
  • Small number of simple fields per row.
  • Internal users who learn the tool deeply.

Design 3

Master-detail split view

List on the left, edit form on the right. Selecting a row populates the form.

    Pros

    • Edit while keeping the list in view — no modal pop-ins.
    • Selection-based navigation is fast (arrow keys, etc.).
    • Form has room for rich fields and validation.

    Cons

    • Eats horizontal space — bad on mobile.
    • Only one item editable at a time.
    • Unsaved changes when switching rows is a UX hazard.

    Best for

    • Desktop-first admin tools (think Mail, Notion).
    • Forms with many fields per item.
    • Workflows where users browse + edit fluidly.

    Design 4

    Card grid with side drawer

    Visual cards matching the customer-facing menu. Edit/delete via hover actions; form slides in from the right.

    Pros

    • Mirrors the live menu — owners see exactly what guests see.
    • Image-forward; great for menus, products, listings.
    • Drawer keeps list visible behind a translucent backdrop.

    Cons

    • Less information-dense than a table.
    • Hover actions are invisible on touch devices.
    • Drawer can feel cramped for long forms.

    Best for

    • Catalogs where visuals matter (food, products).
    • Small-to-medium catalog sizes (≤100 items).
    • Users who think visually, not row-by-row.

    Design 5

    Dedicated add/edit page

    List page links to a separate route (e.g. /admin/menu/:id/edit). Below is a mock of the edit page itself.

    ← Back to menu / Edit item

    Pros

    • All the room you need — supports complex forms and previews.
    • Deep-linkable — share, bookmark, refresh-safe.
    • No layout compromises; works great on mobile too.

    Cons

    • Navigation overhead — extra click to get back to the list.
    • Loses list context; bulk edits are slow.
    • Harder to compare items side-by-side.

    Best for

    • Long forms with sub-sections (pricing, allergens, images).
    • Workflows requiring confirmation steps or wizards.
    • Public/CMS-style content where URL stability matters.

    Recommendation for this app

    Given the menu is image-heavy and the admin already mirrors the customer-facing grid, Design 4 (cards + drawer) usually feels right — it keeps admins anchored in the visual model guests see. If your operators do frequent bulk price changes, layer in Design 2 (inline editing) as a "bulk edit" mode rather than the primary pattern. Avoid mixing modals and drawers in the same screen — pick one.
